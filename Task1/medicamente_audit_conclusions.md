# Медикаменте: аудит конфиденциальности данных

## 1. Выводы аудита

Текущее состояние не обеспечивает управляемый жизненный цикл персональных и медицинских данных: данные распределены между Excel, JPG/PDF, общими папками и файловыми базами 1С; обмены и выгрузки выполняются вручную; централизованный аудит чтения, копирования и изменения данных в описании не указан. При росте числа филиалов и сотрудников риски увеличатся.

Ключевые выводы:

- **Медицинские документы и результаты анализов — наиболее критичная зона.** Сведения о здоровье относятся к специальным категориям персональных данных по 152-ФЗ, а доступ к ним должен быть строго ограничен.
- **Общие сетевые папки и файлы** создают риск неконтролируемого копирования.
- **Excel-реестры пациентов, записей и оплат** дублируют данные, повышают вероятность ошибок и затрудняют исполнение запросов на прекращение обработки или удаление.
- Отсутствие единого подхода к классификации информации
- **Доменная аутентификация сама по себе не обеспечивает авторизацию** на уровне конкретного пациента, медицинской записи или бизнес-операции.

## 2. Карта данных и категории, требующие защиты

| Категория | Примеры | Класс / риск | Минимальные меры |
|---|---|---|---|
| Идентификационные персональные данные (PII) | ФИО, дата рождения, телефон, email, адрес | Персональные данные; позволяют идентифицировать пациента | Шифрование, минимизация, RBAC/ABAC, аудит выгрузок |
| Специальные категории персональных данных | Хронические заболевания, жалобы, диагнозы, анамнез | Данные о здоровье; высокий ущерб при раскрытии | Отдельный домен доступа, строгий ABAC, шифрование, журналирование чтения |
| Медицинские документы | Медкарты, заключения, назначения, сканы JPG/PDF | Медицинская тайна и/или персональные данные в зависимости от содержания | Контроль доступа на уровне документа, DLP; водяные знаки на выгрузках при необходимости |
| Лабораторные данные | Направления, результаты анализов, реестр за день | Данные о здоровье, связанные с конкретным пациентом | Защищённый API, внутренний идентификатор пациента, проверка полномочий |
| Данные записи | Врач, время, услуга, статус записи, напоминание | Могут раскрывать факт обращения за медицинской услугой | Минимизировать текст уведомлений; разделять расписание и медицинскую карту |
| Финансовые данные | Суммы, чеки, оплаты, договоры, возвраты | Финансовые сведения; связка с пациентом повышает чувствительность | Платёжный идентификатор, раздельные роли кассира и бухгалтера, аудит сверок |
| Кадровые и зарплатные данные | Сотрудники, начисления, налоги в 1С | Персональные данные работников и финансовые сведения | Отдельные права бухгалтерии/HR, ограничение экспорта, журнал доступа |
| ТМЦ и закупки | Оборудование, закупки, остатки | Обычно коммерческие данные; не следует смешивать с медицинскими ПДн без необходимости | Отдельный домен доступа, интеграция только необходимых полей |
| Технические метаданные | Логи, идентификаторы, IP, история доступа | Могут содержать ПДн и раскрывать поведение сотрудников или пациентов | Не записывать медицинское содержание в логи; псевдонимизация; ограниченный срок хранения |

## 3. Данные для защиты: способы защиты

| Данные / класс | Шифрование | Обфускация (маскирование) | Обезличивание (псевдонимизация) | Дополнительные меры |
|---|---|---|---|---|
| Идентификационные ПДн: ФИО, дата рождения, телефон, email, адрес | Да — при хранении (БД, файлы, резервные копии) и при передаче (TLS) | Да — телефон, email, адрес в интерфейсах, логах и отчётах | Нет — необходимы для идентификации пациента; присваивается внутренний идентификатор | RBAC/ABAC, аудит, сроки хранения и удаление |
| Специальные категории: диагнозы, анализы, анамнез, сведения о здоровье | Да — при хранении и передаче; шифрование медкарт и сканов | Да — в интерфейсах для пользователей, которым не нужен полный состав | Псевдонимизация для аналитики — внутренний идентификатор пациента вместо ПДн | Строгий ABAC, аудит чтения, защищённый API с полевым доступом |
| Медицинские документы: сканы медкарт, заключений, договоров | Да — шифрование файлов и хранилища, шифрованные резервные копии | Водяные знаки на выгрузках и распечатках | Нет | Доступ на уровне документа, DLP, аудит выдачи |
| Данные записи: врач, время, услуга, статус | Да — при передаче | Частично — в уведомлениях минимум данных (без диагнозов и медданных) | Агрегация в отчётности | RBAC, разделение расписания и медицинской карты |
| Финансовые данные: платежи, чеки, договоры | Да — при хранении и передаче | Да — данные карт в интерфейсах (токенизация) | Псевдонимизация в аналитике — платёжный идентификатор без ПДн пациента | Разделение ролей кассира и бухгалтера, аудит сверок, сроки хранения |
| Кадровые и зарплатные данные | Да — при хранении и передаче | Да — зарплата и банковские реквизиты в отчётах и интерфейсах | Нет | Роли HR/бухгалтерии, контроль экспорта, аудит |
| ТМЦ и закупки | Частично — при хранении (коммерческая тайна) | Нет | Не требуется | Отдельный домен от медицинских данных, интеграция по минимуму полей |
| Технические метаданные: логи, история доступа | Да — хранилища журналов | Да — медицинское содержание в логи не записывается, ПДн маскируются в логах | Агрегация | Неизменяемые логи, ограниченный доступ к журналам |
| Аналитические данные и отчёты | Да — при хранении (аналитическая БД) | — | Да — обезличивание и агрегирование перед загрузкой в аналитику | Витрины с ограниченным набором, доступ по ролям |

## 4. Меры по обеспечению конфиденциальности данных

1. Разграничить права доступа врачей, регистраторов, бухгалтерии и администраторов.
2. Хранить рабочие данные в утверждённых системах, ограничив использование отдельных файлов и общих папок.
3. Организовать защищённый обмен данными с лабораториями и между системами компании.
4. Вести журнал просмотра и изменения медицинских данных.
5. Настроить резервное копирование и проверять возможность восстановления.
6. Определить сроки хранения и порядок удаления данных.
7. Для отчётности использовать отдельную витрину данных с минимально необходимым набором информации.

## 5. Предлагаемая модель тегирования данных

### 5.1. Классификационные теги

| Тег | Что маркирует | Базовое правило обработки |
|---|---|---|
| `PII.DIRECT` | Прямые идентификаторы: ФИО, телефон, email, адрес | Доступ только по рабочей необходимости; не включать в аналитические выгрузки без обоснования |
| `HEALTH.SPECIAL` | Сведения о здоровье: диагнозы, анализы, медицинские заключения | Строгая авторизация, ограниченный круг ролей, аудит чтения и выгрузок |
| `MEDICAL.SECRET` | Медицинские документы и факты обращения, доступ к которым ограничен режимом медицинской тайны | Доступ только уполномоченным сотрудникам в разрешённом контексте; исключения журналировать |
| `FINANCE.PERSON_LINKED` | Платежи и чеки, связанные с пациентом | Раздельные полномочия кассира и бухгалтера; ограничение экспорта и аудит сверок |
| `EMPLOYEE.PII` | Кадровые данные и зарплата сотрудников | Доступ в соответствии с ролью HR/бухгалтерии; контроль выгрузок |
| `CONFIDENTIAL.INTERNAL` | Внутренние бизнес-данные, не предназначенные для публичного раскрытия | Доступ сотрудникам с деловой необходимостью; передача наружу только по утверждённым правилам |

### 5.2. Метаданные управления данными

Помимо классификационных тегов, для управления данными можно использовать метаданные:

| Тег | Назначение | Пример |
|---|---|---|
| `RETENTION:<policy-id>` | Ссылка на правило или срок хранения | `RETENTION:MEDICAL_RECORDS` |
| `PURPOSE:<purpose-id>` | Цель обработки | `PURPOSE:APPOINTMENT` |
| `OWNER:<domain>` | Ответственный владелец домена данных | `OWNER:CLINICAL` |
| `SOURCE:<system>` | Исходная система | `SOURCE:CRM` |
| `LINEAGE:<id>` | Идентификатор происхождения и преобразований данных | `LINEAGE:LAB_IMPORT_001` |

## 6. Единый словарь мер защиты C1–C17

Единая легенда для всех диаграмм потоков данных (DFD) в этой директории. Коды, указанные на потоках, ссылаются на этот словарь.

| Код | Мера | Где применяется |
|---|---|---|
| C1 | Согласие на обработку персональных данных и определение целей обработки до сбора данных | Регистрация, приём |
| C2 | Минимизация данных: собирать и хранить только поля, необходимые для процесса | Все процессы |
| C3 | Классификация и тегирование данных при поступлении, наследование тегов при преобразованиях | Все процессы, ETL, API |
| C4 | Защищённые каналы: TLS 1.2/1.3 для веб, API и интеграций, VPN между сетями | Все потоки данных между пользователями и системами |
| C5 | Шифрование данных при хранении: БД, файлы, резервные копии; ключи хранятся отдельно от данных (KMS) | Все хранилища |
| C6 | RBAC/ABAC и принцип минимальных привилегий: пользователь видит только данные, необходимые для обязанностей | Все доступы к данным |
| C7 | MFA и управление привилегированным доступом к системам и серверам | Доступ сотрудников |
| C8 | Аудит доступа, изменений и выгрузок; неизменяемые логи, централизованный сбор (SIEM) | Все операции с ПДн |
| C9 | DLP: запрет копирования на USB и в личную почту, контроль исходящих данных | Конечные станции, почта |
| C10 | Маскирование (обфускация) персональных данных в интерфейсах, логах и отчётах | UI, логи, выгрузки |
| C11 | Псевдонимизация/обезличивание для аналитики: внутренний идентификатор пациента, агрегация | Аналитический слой, отчёты |
| C12 | Сроки хранения и удаление: удаление по истечении срока и по запросу субъекта | Все хранилища |
| C13 | Шифрованное резервное копирование и регулярная проверка восстановления | Хранилища |
| C14 | Локализация: хранение ПДн граждан РФ на серверах на территории РФ | Инфраструктура |
| C15 | Защищённый API: внутренний идентификатор пациента, полевая авторизация, запрет доступа к данным других пациентов | Интеграция с лабораторией и партнёрами |
| C16 | Водяные знаки на выгрузках и контроль массового извлечения данных | Выгрузки, отчёты |
| C17 | Оценка контрагентов и поставщиков (включая лаборатории), договоры на обработку персональных данных | Взаимодействие с внешними системами |
